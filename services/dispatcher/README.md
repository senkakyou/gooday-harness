# services/dispatcher · 事件驱动的工单状态机

**它不调模型。** 这是刻意的架构决策，不是省事。

## 为什么调度器不能是个会调模型的 bot

让调度经过一个调模型的角色，会引入三个新故障源：

1. **单点故障**——它死了全公司停摆
2. **延迟与成本**——每次流转多一轮模型调用，而流转本身是纯规则
3. **丢失风险**——又多一层「消息已读即凭证消失」

所以：**调度逻辑经过调度中心，数据通道不经过聊天**。
纯规则、秒级响应、不会「想不明白」。
需要判断力的环节（审批、终审、异常分析）才交给会调模型的角色。

## 防诈尸：本文件最贵的一条

`_TRANSITION_EVENTS` **必须从 `TRANSITIONS` 自动派生，绝不手维护白名单**。

> 事故：旧版有 4 个迁移事件不在手写白名单里（`dev_failed`、`rework_approved`、
> `refund_approved`、`refund_recorded`），非法时既不产生决策也不标 processed，
> **永久留成 `new`**。
>
> 平时看不出来。直到工单状态回退——人工重置，或巡检自动重派失败单
> （**这是常态操作**）——旧事件的迁移又变合法，被当新事件「诈尸」重放，
> 把正在跑的单打成 `failed`。**已产出真实交付物的单子就这样被打回。**

三类处理：

| 事件类别 | 处理 |
|---|---|
| 合法迁移 | 执行 ＋ 标 processed |
| 白名单**越权**（未付款就 `dev_done`） | **告警** ＋ 标 processed |
| 其余迁移事件对当前状态非法 | **仅标 processed，不告警**（防诈尸） |
| **非**状态机事件 | 不碰，留给各自的消费者 |

通则：**状态机拥有的事件，遇非法迁移一律消费，绝不留 `new`。**

## 迁移期：影子模式

`mode: shadow` —— 只算不写。旧 dispatcher 仍在跑，
**两个调度器同时改同一张工单的状态是灾难**。

## 判据

1. **状态机 17 项自测全过**，尤其那四个当年漏网的事件逐个验证会被消费。
   *2026-09-07 实测通过。*
2. 影子模式下零写入——决策只落 Event。
3. `_TRANSITION_EVENTS` 是派生的，不是字面量。*自测第 6 项直接验这个。*

## 保留的一个不激活状态

`reviewing` 为「终审外部化」预留，当前终审内嵌在开发进程里，
`dev_done` 直连 `delivering`。

保留一个不激活的状态是刻意的：**改状态机比加状态贵得多**。
