# evaluators/&lt;名字&gt; · 评价什么

> **本文件是模板。** 新增评价器：
> ```bash
> cp -r evolution/evaluators/_template evolution/evaluators/<名字>
> ```

## 评价对象

评价哪一类结果。要具体到"一次什么"——一次工单交付？一集内容出片？一条 bot 回复？

## 输入

- **Result**：被评价的东西本身
- **Evidence**：凭什么判（日志片段、指标、客户反馈、样本）
  —— **没有 Evidence 的评价不算数**，那是拍脑袋

## 打分口径

必须机械可判，不能靠"感觉还行"。写清楚每档的判据：

| 分数 | 含义 | 判据 |
|---|---|---|
| 例 1.0 | 好 | 客户明确接受，无返工 |
| 例 0.5 | 勉强 | 48h 静默默认验收，但有过一次追问 |
| 例 0.0 | 失败 | 客户拒收 / 连续 3 次开发失败 |

**「失败」这一档最重要**——它是第二层循环的燃料。
定得太宽松，系统永远学不到东西。

## 输出

一条 Evaluation，落到 `/var/lib/gooday-harness/evaluations/`：

```json
{
  "target": "<被评价对象的 id>",
  "score": 0.0,
  "verdict": "fail",
  "reasons": ["具体原因，不是'质量不好'"],
  "evidence_refs": ["/var/lib/gooday-harness/evidence/xxx"],
  "at": "2026-09-07T04:00:00Z"
}
```

## 判据

评价器自己也要能被判死刑：

1. 例：**近 30 天内产生过 ≥1 次 `fail`**——从不判失败的评价器等于没有，
   它只会给系统一种"一切都好"的错觉（历史上 patrol 连续三周报"一切正常"，
   而凭据其实早就失效了）。
2. 例：**它判 fail 的样本，人工复核同意率 ≥80%**——低于此说明口径有问题。
