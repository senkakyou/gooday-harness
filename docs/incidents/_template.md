# 事故复盘：一句话标题

> 日期：YYYY-MM-DD · 影响面：谁受影响、多久 · 级别：P0 / P1
> 文件名：`YYYY-MM-DD-短横线标题.md`

## 1. 现象

**用户/站长实际看到的是什么**，不是你后来知道的根因。

## 2. 时间线

| 时刻 | 事件 |
|---|---|
| | 问题实际开始 |
| | 第一个人发现 |
| | 定位到根因 |
| | 修复上线 |

> **「问题实际开始」到「第一个人发现」的间隔是本次复盘最重要的数字。**
> 这个间隔大，说明检测缺失——那才是要修的东西，而不只是那个 bug。
> 参照：凭据失效那次，这个间隔是 **三周**。

## 3. 根因

不是「某某写错了」。往下追三层：
为什么写错了 → 为什么没被测出来 → 为什么没被监控发现。

**最有价值的根因形态是「结构要求人记得做某事」**——
人不会记得，所以那不是人的问题，是结构的问题。

## 4. 为什么没早点发现

- [ ] 根本没有这项监控
- [ ] 有监控但阈值不对
- [ ] 有监控但**对这种失败形态静默跳过**（最危险，看起来一切正常）
- [ ] 有监控但告警被淹没在噪音里
- [ ] 有日志但看不出真因（真实错误被无关警告顶掉）

## 5. 产出的规范（**必填**）

| 编号 | 内容 | 能自动检查吗 | 检查器 |
|---|---|---|---|
| G?? | | 是 / 否 | `evolution/gates/rules/G/gNN_xxx.py` |

写不出检查器的，要么改写成能检查的形式，
要么明确标「人工」并在 `ops/runbooks/` 给它一个端到端验收动作。
**两样都没有 = 这次复盘走过场了。**

## 6. 验证

- [ ] 端到端复现原场景，确认不再发生
- [ ] 动了常驻服务？确认**进程启动时间晚于代码 mtime**
- [ ] **新检查器在修复前的代码上会红** —— 在坏代码上也不报警的检查器，等于没写

> 最后一条最常被跳过，也最关键。
