# 事故复盘：bot 的长回复被整条丢掉，日志里没有真因

> 日期：2026-09-08 · 影响面：所有 bot 对所有人，回复超 4000 字即丢，
> 已知实际丢失 1 份（灵犀的架构评审）· 级别：P1

## 1. 现象

站长请灵犀对一份文档改动做对抗性评审。灵犀**收到了、处理了、写完了**，
站长这边**什么都没收到**。

服务列表全绿、心跳正常、`systemctl is-active` 是 active。
唯一的痕迹是 `/var/log/gooday-harness/bot-lingxi.log` 里三行：

```
[bot-lingxi] 发送 HTTP 400（第 1 次）
[bot-lingxi] 发送 HTTP 400（第 2 次）
[bot-lingxi] 发送 HTTP 400（第 3 次）
[bot-lingxi] ⚠️ 发送最终失败 → 1
```

**三行一模一样的报错，看起来像网络抖动。** 真因（内容超长）一个字都没有。

## 2. 时间线

| 时刻 | 事件 |
|---|---|
| 2026-09-07 起 | 问题实际开始——bot 迁进新架构起就存在，只是没人写过这么长的回复 |
| 2026-09-08 04:22 | 站长发出评审请求 |
| 2026-09-08 约 04:30 | 灵犀写完回复，三次 400 后丢弃 |
| 2026-09-08 04:32 | 站长侧轮询 10 分钟没等到回复，去看 bot 日志才发现 |
| 2026-09-08 04:34 | 定位根因、修复上线、6 个 bot 重启 |

> **「实际开始」到「被发现」隔了约一天，但那是运气**——
> 这段时间里没人写过超过 4000 字的回复。真正的问题是：
> **它被发现完全靠人恰好在等一个回复。** 没有任何监控会报这件事，
> 短回复正常时它和「一切正常」长得一模一样。

## 3. 根因

往下追三层：

1. **为什么写错了**——`packages/botkit/outbound.py` 不知道服务端有 4000 字上限。
   服务端 `PrivateMessageController` 判 `content.Length > 4000` 返回 400，
   这个数**只存在于服务端**，客户端没有任何声明。
2. **为什么没被测出来**——`test_botkit.py` 的发送用例都是短文本。
   而且 `send_segments`（分段发送）**当时就在同一个文件里，第 96 行**，
   只是没有任何人调用它：runner 直接把整段回复塞给 `send`。
3. **为什么没被监控发现**——`send` 把 400 当可重试错误重试 3 次。
   三次必然失败，而重试把「请求本身是坏的」伪装成「网络不稳」。
   失败后只打一行「发送最终失败」，不带状态码语义、不带响应体、不带内容长度。

**结构性根因**：`send_segments` 是「能力写好了但没接上」。
这和「注入防御条款写进文档三个月没进任何 bot 的 prompt」、
「drop-in 装上了但安装脚本没记」是**完全同一个形状**——
东西存在，但不会自动生效。本项目存在的理由就是消灭这个形状。

## 5. 产出的规范（**必填**）

| 编号 | 内容 | 能自动检查吗 | 检查器 |
|---|---|---|---|
| G21 | 客户端 `MAX_CONTENT` 与服务端 `content.Length > N` 对齐；**每个直发 `/api/messages/` 的文件都要认识这个上限**；4xx 一律不重试（401 除外） | 是 | `evolution/gates/rules/G/g21_limit_alignment.py` |

为什么不查「有没有调用 split()」：那要做调用图分析，用 grep 做只会误判。
**能机械判定的是限值对齐与作用域覆盖**，剩下的靠两层兜底——
`send()` 自己分段（调用方想漏也漏不掉）＋ 4xx 早退时日志直接说
「内容 N 字，超过上限 4000」。

### 第一版规则漏了：窟窿不在调用图，在作用域

初版 G21 只盯 `packages/botkit/outbound.py` 一个文件，**报绿**。
而这台机器上有四处直发 `/api/messages/`，另外三处各自手搓了发送函数：

| 文件 | 产什么 | 当时认识 4000 吗 |
|---|---|---|
| `workflows/daily-report/run.py` | 日报 | ❌ |
| `workflows/finance-report/run.py` | 财报 | ❌ |
| `workflows/coo-patrol/run.py` | 巡检报告 | ❌ |

**全是最容易写长的那类，收件人还都是站长。**
`coo-patrol` 最讽刺：它 import 了 `outbound` 只借 `allowed()` 做白名单，
注释里还写着「harness 本来就有这个能力，不该复制第二份（G03）」——
**结果只借了半个能力，另一半的坑照样踩。**

三处均已改为复用 `outbound` 的 `MAX_CONTENT` / `split()`，G21 作用域已扩到
`packages/` `workflows/` `services/` 下所有 `.py`。（2026-09-08 灵犀评审指出）

### 顺带修掉的两处检查器假绿

同一轮评审还翻出两个**检查器被自己的文字满足**的例子：

- `g04` 要求 install.sh 有 `ops/nginx/*` 通配扫描——改写后代码里已经没有了，
  **是注释里那句「原来 glob 写成 ops/nginx/*.conf」在满足它**。
- `g17` 要求 `.pre-commit-config.yaml` 真的调用 check.py——
  **把那行注释掉，G17 照样绿**。同一天、隔壁文件、完全同形。

统一收进 `evolution/gates/rules/_srclib.py` 的 `code_only()`：匹配前剥掉整行注释
与单行字符串字面量。跨行字符串不处理——**做一半的词法分析比不做更危险**。

`g17_gates_wired.py` 的 docstring 第一行还写着「G11 门禁必须被自动触发」，
而 `RULE = "G17"`：文件里正好记着「2026-09-07 新写的门禁规则误用了已被占用的 G11」——
**号改了、docstring 忘了改，事故的化石留在原地。** 已一并修正。

### 第二轮评审：修完还剩四处（灵犀 2026-09-08 复验）

**1｜规则自己没吃自己那副药。** `g04`/`g17` 都堵了「被注释满足」的洞，
**唯独当事人 `g21` 还在用原始文本**——一行 `# TODO: 之后复用 MAX_CONTENT`
就能让它报绿而 bug 原样在。而 g21 正是这整轮的第一条。已改用 `code_only()`
（只剥注释、**不剥字符串**——`/api/messages/` 恰恰长在 f-string 里，
剥了字符串这条规则就永远找不到发送方，那是更糟的假绿）。

**2｜假绿没消除，只是换了个段落。** 第一版只在 nginx 段置 `INSTALL_FAILED`，
而 `.env` 缺失、`Jwt__Secret` 空展开、服务 `enable`/`restart` 失败三处仍是光 echo
然后 exit 0。**脚本末尾那句「前面每一处都置了标志」当场变成假话。**
按 install.sh 自己记着的教训，`Jwt__Secret` 空展开 = 整站每个请求 500，
比 nginx 语法错重得多。四类现已全部置标志。

**3｜剥字符串下手过宽，制造了两个假红。** 理由（echo 里的提示语不算扫描）对，
实现（无差别剥掉所有单行引号内容）错。灵犀给了两个实测反例，都是常见写法：

| 完全合法的写法 | 剥完 | 假红 |
|---|---|---|
| `for dir in "$REPO/services"/*/` | `for dir in /*/` | ❌ G04「没有扫描 services/」 |
| `entry: "python3 …/check.py ."` | `entry:` | ⚠️ G17「pre-commit 未接入」 |

**现在能绿只是因为本仓库恰好把引号闭在了别处——那是靠写法运气，不是靠规则。**
改法：`strip_echo` 只剥 `echo`/`printf` 的引号参数（YAML/Python 一律不剥），
再把 G04 的模式放宽成 `services["']?/\*` 以容纳引号写在中间的合法形态。
三种引号风格实测全绿，而 echo 里的字符串仍不算数。

**4｜「铁律 3」三处都只做到一半。** 三个 workflow 各自搓了分段循环，
**全都漏了「最后补一条『第 x/y 段失败』」**——收件人看到的还是半截话，
而且不知道是半截。`coo-patrol` 更松：只返回最后一段的结果，
前面段失败调用方完全看不见。它注释里刚自嘲过「只借了 allowed() 没借 split()，
只借了半个能力」，**借了 split() 不借补报，还是半个**。
已抽出 `outbound.send_each(content, send_one)`：分段、逐段发、失败补报三件事
只写一份，三处全部改用它。

> 顺带一个连带 bug：`_srclib.py` 提交之后 G09 报「命名不合规」——
> 它按 `<层><NN>_xxx.py` 要求所有 `rules/**.py`，而 `_` 开头是模板/内部件、
> `load_rules` 自己就跳过。**未跟踪时不报、一提交才报**，症状还带延迟。已修。

### 第三轮评审：同一形状的第三、四次换皮（灵犀 2026-09-08）

**1｜UTF-16：我把「盲点」的严重性判错了。**
原文写「靠分段前缀预留的 16 字余量兜着，够用」。**那个推理是错的**——
误差不是有上界的常数，是跟段内 astral 字符**线性相关**：一段里 17 个 🔴 就破，
而日报的优先级标恰好是 🔴🟠⚪🔵，**全是 astral**。
更阴的是破的时候：`send` 里「内容超长」那句提示用同一个 `len()` 判，
恰好判为假 → 不分段、不打印、直接吃 400，**真因又一次不进日志**。
已加 `outbound.ulen()`（按 UTF-16 码元数），`split` / `send` / `send_each` 全部改用它。

**2｜G04 假绿的第三次换皮：注释 → echo → heredoc。**
`install.sh` 末尾 `cat <<'EOF' … EOF` 的收尾提示里写着 `/var/lib/gooday-harness/state`，
而判据是**裸子串** `d in src` —— 于是把真正的 `install -d` 整行删掉，规则照样绿。
两道都补上：`code_only(strip_heredoc=True)` 剥 heredoc 正文；
判据改成「同一行上必须有 `install -d` / `mkdir -p`」（并先接反斜杠续行）。
实测：删掉所有建目录命令、只留 heredoc 提示文本 → 三条全报（修前三条全绿）。

**3｜作用域窄在语言维度上。** 上一版把作用域从「一个文件」扩到「所有 .py」，
**但前端根本不在管辖内**。这里要给灵犀的结论改一处：她说「同一个上限现在有
1000/500/4000 三个数」——实测不是。`ChatBox.jsx` 走的是 SignalR，
而 `ChatHub.cs:40` 自己判 `content.Length > 500`，**它的 `maxLength={500}` 是对齐的**。
真正没对齐的只有 `Messages.jsx`：私信走 REST（4000），它写 1000。
所以 G21 的前端判据按**端点**分而不是按数字分，现报一条 WARN。

**4｜补报文案我写了两份。** `send_each` 和 `send_segments` 各一遍，
措辞还不一样（「内容不完整」vs「内容可能不完整」）——
**刚引用完 G03 单一真源，转手就造了第二份**。已抽出 `run_segments()`，两边都走它。

**5｜`Jwt__Secret` 空值判据可能是假绿。** compose 把空值渲染成 `""`，
那是两个非空字符，`[[ -z ]]` 会判成「有值」放行。已加去引号，实测两向正确。

> 我自己在修 heredoc 时又摔了一次同样的跤：第一版的 heredoc 正则把
> `END_MARK="# <<< gooday-harness managed block <<<"` 这个**字符串常量**
> 当成了 heredoc 开头，从那行起整个文件后半段被丢掉，G04 当场报两条假红。
> 摔的正是 `_srclib.py` 自己写着的那句「做一半的词法分析比不做更危险」。
> 已改成排除 `<<<` 且只认引号外的 `<<`。
> **好在方向是安全的一侧：症状是假红（看得见），不是假绿（看不见）。**

### 新发现的两条，未修（要拍板）

- **`ChatBox` 的输入上限严于服务端**（1000 vs 4000 那条是 `Messages.jsx`）——
  用户打到上限静默打不动，没提示没字数计数。改数字是产品决定，记账不动手。
- **`ChatHub.SendMessage` 对超长/空内容是 `return;`**——
  **服务端静默丢弃，客户端收不到任何反馈**。这是 C09「异常必给回执」的形状，
  但它在实时聊天路径上，改动要谨慎。记在这里，别让它烂掉。
