# 006 · Learn 与 Improve 为什么暂不自动化

> 2026-09-07 · 状态：**已定，刻意不做**
> 补 `docs/specs/002-known-gaps.md` 缺口二——这是最后一个未闭合的缺口。

## 现状

第二层循环六环，四环有执行体，两环靠人：

| 环 | 谁在做 |
|---|---|
| Evaluate | ⚠️ `evolution/loops/*` 自带判据；`evolution/evaluators/` 有框架但**零成员** |
| **Learn** | ❌ 人写 `docs/incidents/` |
| **Improve** | ❌ 人写 `docs/decisions/` |
| Experiment | ⚠️ `evolution/loops/*` 内置前后对比；`evolution/experiments/` 有框架但**零成员** |
| Gate | ✅ `evolution/gates/` |
| Promote / Rollback | ✅ `ops/install.sh` ＋ checkpoint |

> 2026-09-08 订正：原表把 Evaluate / Experiment 标成 ✅ 并指向那两个目录，
> 但它们至今只有 `_template/`。真正在跑这两环的是 `evolution/loops/` 下的闭环。
> **「目录存在」不等于「里面有东西在跑」**——这正是本项目反复栽的那个形状。

## 结论：暂不自动化，而且要明说

**说「系统会自我进化」而这两环是人在跑，是自欺。**
所以本文件的第一作用是把这句话写下来，而不是把它藏起来。

## 为什么不做

### 一、今天的证据不支持

今天一天，第二层循环真正产出的改进有 8 条，全部来自**人（或 AI）在真跑时
发现的东西**，没有一条是评价器打分打出来的：

- trace 写不进去时 patrol 报「一切正常」——**跑起来才发现**
- install.sh 装的是三小时前的代码——**跑起来才发现**
- 停了旧 cron 忘了装新的——**跑起来才发现**
- 检查器自己的假阳性 ×6——**每一个都是真跑才暴露**

**Evaluate 环产出的信息量，远小于「真跑一次」产出的。**
在这个比例下自动化 Improve，等于让系统基于最弱的信号去改自己。

### 二、Improve 自动化的失败模式很难发现

一个会自动提改动方案的系统，最可能的失败不是「提了个坏方案」——
那还容易发现。而是**持续提一堆看起来合理、实际无关痛痒的小改动**，
把人的注意力磨光，直到没人再认真看它的提案。

那时候它就变成了噪音源，而且是带着「自我进化」光环的噪音源。

### 三、缺的不是自动化，是数据

现在 `evaluations/` 里只有 patrol-agreement 一个评价器、几条记录。
在这个数据量上谈「根据评价结果自动改进」是空的。

**先把 Evaluate 环喂饱，再谈 Improve。**

## 那什么时候重新考虑

三条都满足时：

1. **评价器 ≥5 个，且覆盖不同维度**（现在 1 个）
2. **连续 30 天有评价数据，其中至少 10 次判 `fail`**
   ——从不判失败的评价体系，自动化了也只会输出「一切都好」
3. **人工复核这些 fail，同意率 ≥80%**
   ——评价口径本身不可信时，基于它的自动改进只会放大偏差

三条任一不满足，就继续人来跑这两环。

## 现在做的（低成本，不叫自动化）

**Learn 环加一个归档动作**：评价器判 `fail` 时，
除了写 Evaluation，另外在 `docs/incidents/` 提示需要人写复盘。
这不是自动化 Learn，是**让「该写复盘了」这件事不依赖人记得**。

Improve 环不动。
