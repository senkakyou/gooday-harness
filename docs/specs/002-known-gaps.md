### nginx 的真实情况（比"冲突"严重）

实测发现**宿主机根本没有 nginx**（`systemctl is-active nginx` → inactive）。
nginx 跑在容器 `gooday_nginx` 里（host 网络模式），配置来自
`/opt/gooday/nginx/conf.d` 的 bind mount，已占 **80/443** 与
`www.gooday.ltd gooday.ltd`。

原 `install.sh` 往 `/etc/nginx/conf.d/` 写 —— 写入成功、脚本全绿、**零效果**。
比冲突更难发现，因为什么都不报。

已改为：

1. **装前预检**端口与 server_name 冲突（实测能识别 443 与两个 server_name）
2. **装后验证生效**——没有任何 nginx 在读该目录时，明确打印「当前不生效」
   而不是假装成功
3. 教训固化为 **G08 部署必须验证生效**（已实测：在修复前的代码上会红）

### 切换后的真实形态（2026-09-08 实测订正）

原文写的是「装进本项目自己的 `/opt/gooday-harness/nginx/conf.d/`，
迁移期新配置写好但不生效，切换时才把本目录挂进 nginx 容器」。**切换已经发生，
而挂进去的不是那个目录**——`ops/docker/docker-compose.yml` 里写的是
`../nginx/nginx.conf`、`../nginx/conf.d`、`../nginx/certs`，
相对 `ops/docker/` 解析出来正是 **`ops/nginx/`**。

实测证据（2026-09-08）：

```
docker inspect gooday-harness-nginx → Source=/opt/gooday-harness/ops/nginx/conf.d
容器内 /etc/nginx/conf.d/gooday.conf   inode 567927
宿主 ops/nginx/conf.d/gooday.conf      inode 567927   ← 同一个文件
宿主 /opt/gooday-harness/nginx/conf.d/ 里【没有 gooday.conf】
```

所以：**`ops/nginx/` 既是真源也是运行期挂载点，中间没有拷贝这一步。**
它是 G03「配置跟归属方走且只有一份」的一个特例——真源直接被容器读，
改完 `nginx -t && nginx -s reload` 即生效，不经过 `install.sh` 拷贝。

> 由此暴露的 install.sh 缺陷已于 2026-09-08 修掉，见本文件缺口八。

## 缺口六：上传白名单与 MIME 注册不一致（迁入应用时发现）

`Program.cs` 只注册了 7 种 MIME（epub / srt / lrc / z01-03 / apk），
但上传白名单允许 **.7z / .bat / .rar / .aac** 等类型。

**这四类传上去会 404**——和当年 `.epub` 那个坑同款：
`UseStaticFiles` 只服务内置 MIME 列表里的扩展名，未注册的一律 404。
文件传上去了、数据库有记录、页面列得出来，**点下载才 404**。

目前没有这些类型的文件，所以是潜在风险不是当前故障。
由 policies G15 每次检查时提示，**2026-09-08 实测为 27 条 WARN**
（原文写 26，是加 `services/web/` 之前的数）。

**修法**：要么给这些扩展名注册 MIME，要么从上传白名单里去掉。
两者必须一致——**允许上传却服务不了，是最糟的组合**。

## ~~缺口八：install.sh 把 nginx 配置拷进没人读的目录~~ ✅ 2026-09-08 已闭合

修完「别往 /etc/nginx/conf.d 写」之后，`install.sh` 改成拷进
`/opt/gooday-harness/nginx/conf.d/`。而容器实际挂的是 `ops/nginx/conf.d`
（compose 里的 `../nginx/conf.d` 相对 `ops/docker/` 解析而来）。

于是每次安装：拷贝落进无人读的目录 → 紧接着 `docker exec nginx -t && reload`
**成功**（容器读的本来就是对的那份）→ 脚本打印 ✅。
**拷贝零效果，验证却全绿。** 这正是 G08 要防的形状，被 G08 自己的实现犯了。

同段还有第二个错：glob 写作 `ops/nginx/*.conf`，抓到的是主配置 `nginx.conf`、
漏掉 `conf.d/gooday.conf`。那份 `nginx.conf` 里有 `events{}`，
真被当成 conf.d 片段加载时 nginx 会直接起不来。

**已闭合**（2026-09-08）：

1. 真源即挂载源，**不再拷贝**；`NGINX_DIR` 指向 `ops/nginx/conf.d`
2. 验证顺序倒过来：**先证明容器挂的确实是这个目录**（`docker inspect` 取挂载源，
   `readlink -f` 归一后比对），再验语法并 reload。挂错时报 ❌ 并给出重建命令
3. `g04_deploy_rebuildable.py` 匹配前先**剥掉整行注释**——
   修之前它是被那段注释里的 `ops/nginx/*.conf` 满足的，**一个能被注释满足的
   检查器是假的**。实测：把 glob 换回变量形式，G04 立刻报红

遗留：`/opt/gooday-harness/nginx/`（root 属主、未跟踪）是那次错拷留下的空壳，
删掉即可，删之前确认没有任何容器挂着它。

## 缺口十二：检查器与被检对象在同一抽象层 —— 修复动作会重新生成被检测物

2026-09-08 一天之内，同一形状换了四次皮：注释 → `echo` 提示语 → heredoc 正文 →
修 heredoc 的正则把字符串常量当成 heredoc 开头。**每次修完，下一种写法又能骗过它。**

根因不是「又漏了一种写法」：`gates/rules/` 的判据是 grep 源码文本，
而被判对象也是源码文本——**两者在同一抽象层，动一个就能骗过另一个**。

已做的是把「对抗样本」写进 `policies/00-index.md` 的加规范流程：
新检查器除了「在修复前的代码上会红」，还要**拿修复手法本身造一个样本，确认它也会红**。
判「剥错倒向哪边」的准绳是：倒向假红（看得见）安全，倒向假绿（看不见）危险。

**没做的是把它变成检查器**——「每条规则有没有配对抗样本」目前没有自动判定，
靠写规则的人自觉。这本身就是本项目最痛恨的形状（规范有、检查器没有），
所以记在这里，别装作已经解决了。

## 缺口十四：出口白名单不是唯一的门，而它自称是

`packages/botkit/outbound.py` 原话：「这张表是**结构性防线**：即使 bot 被注入说服了，
它也发不出去。」

**这句话把覆盖面吹大了。** `workflows/dev-requests` 与 `workflows/chengyu-upload`
直接 `INSERT INTO PrivateMessages`，根本不经过 `outbound`，`allowed()` 一次都不会被调用。

现状风险有限：那两处的收件人都由业务数据固定（需求单的 `UserId`、站长），
不是内容里能指定的——所以「注入让它发给任意人」这条路走不通。
**但「防线只覆盖走这扇门的调用方」必须写明**：
吹大的安全声明比没有声明更危险，因为它会让人不再去看别的路。

已做：把 `outbound.py` 里那句话改成准确的。
未做：**让所有出站消息只有一扇门**（把直接写库的两处收进 `outbound`，
或给出一个带白名单的 `insert_pm`）。那是设计变更，请站长拍。

> 2026-09-08 灵犀评审指出。她的框架比现状更悲观（她按"客户可控文本"推），
> 我核过收件人来源后判断风险低于她的描述——**但她指出的结构问题成立**。

## 缺口十五：API 里的「即时触发」是空转，且失败形状完全无声

`services/api/src/Controllers/DevRequestController.cs` 在客户提交需求后
`Process.Start("/usr/bin/python3", "/opt/gooday/scripts/handle-dev-requests.py")`。

三层都不成立：那个路径 2026-09-07 已改名；**本服务跑在容器里**，
compose 只挂了数据卷与产物目录，容器里从来没有这个脚本。

**失败形状比「路径写错」更隐蔽**：`FileName` 是 `/usr/bin/python3`，
**进程启动是成功的**，所以 `catch` 一个字都不会触发；是 python3 自己 rc=2 退出，
而 `RedirectStandardError=false`、fire-and-forget 没人收退出码。
于是「客户提交后即时处理」**100% 静默失效**，而注释里那句「cron 兜底」正好把它盖住。

已做：删掉这段死代码，注释写明为什么，并说清现在只有 cron（最坏延迟 20 分钟）。
**注意：这是 C# 源码改动，需要重建 api 容器才生效**——
在那之前生产行为不变（本来就是空转，所以不重建也不会更坏）。
要恢复「即时」得给它一条真通道（共享卷放触发文件，或内部 HTTP 触发点），
不是假装 `Process.Start` 能跨过容器边界。

> 同一轮还修了 `ChatHub.SendMessage`：`content.Trim()` 在 `IsNullOrEmpty` 之前，
> **null 会在 Trim 那行就抛 NRE，于是判空里的 Null 那一半是死代码**。
> 形状同 `math-episodes` 的 `SPEC_DIR` 双重赋值——前一句让后一句的一半永远到不了。
> 同样需要重建容器才生效。

## ~~缺口十六：`try/except` 只挡「进程起不来」，挡不住「跑了但没干成」~~ ✅ 2026-09-08 已闭合

同一形状在三处独立出现，**每一处的损失都落在客户那一侧**：

| 位置 | 表现 |
|---|---|
| `DevRequestController.cs` 的 `Process.Start` | 进程启动成功 → `catch` 永不触发 → python3 自己 rc=2 而没人收 |
| `dev-requests` 的 `call_claude_for_reply` | claude 起得来就不进 `except`：非零退出、认证过期、输出格式变了，全都变成 `text=""` |
| `chengyu-upload` 的 `db()` | 只取 `.stdout`，INSERT 失败返回空串 |

中间那条最完整：空 `text` → **空白私信写进库** → 日志照打「已发私信给 X」→
状态推到 `talking` 并打上 `[如意已收]` → 下轮被 MARKER 过滤，**永不重试**。
**客户收到一条空白消息，而单子上写着「已回复」。**
更讽刺的是：同一轮刚被改对名字的降级模板，**在最可能的失败形态下根本到不了**。

第三条同族：`db()` 失败返回空串，调用处照样 `write(maxno)` 推进度、打印「已推 N 集」。
`PUSHED` 单调前进不可退——**那批集子从此永远不再推**，而日志写着成功。

**已闭合**（2026-09-08）：

1. `call_claude_for_reply` 显式判 `returncode != 0` 与 `not text.strip()`，
   两者都 `raise` → 真正掉进 `except` 走降级模板
2. `insert_pm` 加第二道防线：**content 为空拒绝写库**
3. `chengyu-upload` 的 `db()` 失败即 `raise`，`write(PUSHED)` 因此到不了，下次会重推

> 遗留（小，已知）：分段写库时若第 2 段失败，第 1 段已落库、进度未推进 →
> 下次重推会产生重复。**重复 ≠ 永久丢失**，这个方向是对的，不改。

> 三处的共性：`try/except` 的覆盖面是「调用能不能发起」，
> 不是「事情有没有办成」。**别让 except 的存在给人已经处理了错误的错觉。**
