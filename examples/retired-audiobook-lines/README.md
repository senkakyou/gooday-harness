# 已退役：两条依赖听书模块的产线

> **状态：已退役（2026-09-08）。** 站长清空了听书模块，两条产线的产出无处可去。
>
> 照 [`retired-patrol-agreement`](../retired-patrol-agreement/README.md) 的做法搬到这里：
> 从 `workflows/` 移出是**刻意的**——那是扩展点，`ops/install.sh` 会通配扫描
> `workflows/*/deploy/schedule.cron` 并装进 crontab。死产线留在扩展点目录里，
> 会每天定时跑、每天失败、每天在日志里留一条没人该管的记录。
>
> 执行入口与 cron 片段都已改名加 `.txt`，**任何发现机制都扫不到**。

## 它们为什么必须退役，而不是留着"以后可能有用"

**留着不动的代价不是零。** 退役前实测（2026-09-08）：

| | 定时 | 实际在干什么 |
|---|---|---|
| `math-episodes` | 每天 02:00 | 当天 **成功 0 集、失败 20 集**；上架目标 `BOOK_ID=18`（奇妙数学）已被删，就算生成成功也无处上架 |
| `chengyu-upload` | 每 3 天 21:00 | 日志永远是「无新集，跳过」——看着完全正常 |

`chengyu-upload` 那条尤其值得记：它打印「无新集」**不是因为真的没有新集**，
而是 `sudo -n sqlite3 -separator … <db>` 的参数顺序不匹配 sudoers 白名单
（白名单要求 db 路径紧跟命令名），每次都因缺密码失败 rc=1，
而旧代码 `return subprocess.run(...).stdout` 把失败吞成空串 → 空列表 → 「无新集」。

> **「查不了」被当成「没问题」，日志里那一行和正常运行一模一样。**
> 这是本项目最痛恨的形态，而它在这条产线上活了很久没人发现。

## 留着的价值：里面的硬知识不该跟着产线一起死

- **edge-tts 音色必须在探活白名单内**（policies G13）——用了已下线音色会产出
  43 段永久 0 字节，而重试逻辑把它当限流，空转一小时等一个永不会来的窗口
- **SVG 逐帧 + Playwright 截图**的出片管线（`math-build.py.txt`）
- **`flock -n` 防叠跑**：2G 内存的机器上两轮并发必然 OOM
- **选题池 0 基索引 + 主池含重复**的计数坑（`math_pool.py.txt`）

## 什么条件下会复活

听书模块重建、且确定要恢复对应内容线时：把目录移回 `workflows/`、
去掉 `.txt` 后缀、**把 `BOOK_ID` / `BOOK` 改成新的书 Id**，
然后 `sudo bash ops/install.sh` 让 cron 生效。

复活前必须先修的两处（退役时已知未修，因为改了也没处验证）：

1. `chengyu-upload` 的 `sudo sqlite3` 参数顺序（db 路径必须紧跟命令名）
2. 两条线的 README 判据都还写着「每天出片 ≥20 集」这类**当时的**指标，
   复活时要按新目标重写——**照抄一个不成立的判据比没有判据更糟**
