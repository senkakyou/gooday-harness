# workflows/db-snapshot · 数据库快照

每小时一份在线热备，滚动 24 份；03 点档归档日快照保留 7 份；04 点档做恢复演练。

从旧 Gooday 的 `db-snapshot.sh` **重新设计**，保留它三条硬知识、补它一个缺口。

## 保留的三条（都别删）

**① 用 `sqlite3 .backup` 在线热备，不用 `cp`。**
WAL 模式下写入先落 `-wal` 文件，直接 `cp` 主文件会得到一份
「看起来正常但缺最近写入」的快照。这种损坏**不报错**，
只在你真的需要恢复的那天才发现（policies G14）。

**② 备完立即校验：`integrity_check` ＋ 关键表非空。**
文件完整不等于数据在——「备份成功但内容是空的」是真实存在的失败形态。

**③ 校验通过才替换正式位。**
上一份好快照在此之前一直保留。否则一次失败的备份会顺手毁掉上一份能用的。

## 补的一个缺口：恢复演练

旧脚本验证的是「备份文件完整」，**从没验证过「这份备份能恢复」**——
而后者才是你真正需要的那个。

每天 04 点档把最新快照当成真要恢复的那份，复制出来、打开、查关键表。
**备份体系最危险的状态不是没备份，是以为有备份。**

## 跑

```bash
cp config.example.json config.json    # 改备份目标
python3 run.py
```

失败时落 `.snapshot-failure` 标记并以非零退出；
恢复正常后标记自动清除（否则标记会永久挂着，变成没人再看的噪音）。

## 产出与监控

| | |
|---|---|
| 快照 | `/srv/gooday-harness/backups/<目标>/{hourly,daily}/` |
| 失败标记 | `/srv/gooday-harness/backups/.snapshot-failure` |
| 监控者 | `workflows/patrol` 的 `checks/backups.py`——查失败标记与最新快照年龄 |

**生产者和消费者要配对**：只有备份没有监控，等于把「备份停了」这件事
交给运气。patrol 会盯着它。

## 判据

1. **失败时上一份好快照必须原封不动。**
   *2026-09-07 实测：源库损坏 → 备份失败 → 好快照 md5 未变，标记已落，退出码 1。*
2. **恢复演练必须真的能打开并查到数据。**
   *实测：演练通过，Users=15 行。*
3. **失败标记必须在恢复正常后自动清除**——永久挂着的标记会变成没人看的噪音。
   *实测通过。*
4. 最新快照年龄 ≤3 小时，由 patrol 持续监控。

## 停摆判定

`/srv/gooday-harness/backups/<目标>/hourly/` 最新文件超 3 小时未更新 = 停摆。
判活看**产物 mtime**，不看日志——cron 静默失败时目录还在、看起来很正常。
