# workflows/patrol · 系统看门狗

每 5 分钟一轮，检查系统有没有在坏，坏了就说清楚坏在哪、凭什么这么判、该怎么办。

这是从旧 Gooday 迁过来的第一个真实业务，**重新设计而非搬运**——
保留的是它的知识（阈值、判据、踩过的坑），不是它那 707 行代码。

## 与退役的 coo-patrol 有何不同

> 旧的 `lingxi-coo-patrol.py` 已于 2026-09-07 退役。它的 8 项工单流业务检查
> 当时迁到了 `workflows/coo-patrol`，而**那条流程已于 2026-09-11 整个删除**
> （docs/decisions/006）：新架构没有自动状态流转，也就没有「工单卡在某状态」
> 这回事；它剩下的「服务存活 / 收件箱积压」本工作流已经在做。
>
> 唯一真正需要接回来的是「躺着不动的订单要提醒」，现在在
> `workflows/daily-report` 里（灵犀每天 09:00 那份）——放那里是因为
> **patrol 只把发现写进证据链、不给人发消息**。

| | 旧 | 新 |
|---|---|---|
| 结构 | 707 行单文件，14 项巡检写在一起 | `checks/` 一项一个文件，`run.py` 递归发现，新增不用改入口 |
| 目标 | 服务名、路径、阈值全写死在代码里 | 走 `config.json`，换库换服务不用改代码 |
| 处置 | 直接动手 | **按动作分级**：幂等可回滚的才自动做，其余任何模式下都转人工 |

## 影子模式（迁移期用过，现为 active）

`mode: shadow` —— 只记 `action_suppressed` 事件，不执行任何处置。
迁移期新旧两个 patrol 并存时必须用它：两个看门狗抢着重启同一个服务会互相打架，
一个正在重启、另一个判定它没起来又重启一次。

**2026-09-07 切换后 `config.json` 与 `config.example.json` 的 mode 都是 `active`。**
但安全性不再靠这个开关兜底——见下面判据第 2 条：不可逆动作与 `mode` 无关，
任何模式下都不自动执行。`shadow` 保留下来是为了下次做类似并存切换，不是现行状态。

## 跑

```bash
cp config.example.json config.json    # 改巡检目标
python3 run.py                        # 手动跑一轮
```

有 P0/P1 时以非零退出，cron 日志和外层监控能据此察觉。

## 现有巡检项（11 项，`run.py` 递归发现）

| | 查什么 |
|---|---|
| `services` | 进程死活 **＋ 活着但卡死**——bot 卡死 8 次，全程 `active (running)`，心跳几十分钟没动，无人发现 |
| `credentials` | 凭据缺失 / 过期 / 属主漂移——旧 patrol **有这项检查却仍报了三周「一切正常」**，因为它对「文件不存在」是静默跳过的 |
| `stale_process` | 进程比它的代码还旧——「改了但没 restart」探测 |
| `bot_inbox` | 收件箱有没有在消化，**两个方向都查**（堆积、和对同一条消息连回 14 遍） |
| `db_health` | 数据库能不能打开、完整性、有没有卡在锁上 |
| `backups` | 备份新鲜度与失败标记——最危险的不是没备份，是**以为有备份** |
| `certs` | TLS 证书到期——典型的「安静地烂掉」，过期前没有任何东西会报错 |
| `assets` | 已发布内容的文件还在不在（后台正常、点进去 404） |
| `config_drift` | `config.json` 缺了 `config.example.json` 里新增的配置段 |
| `migration` | 被替代的旧任务与替代它的新任务，**必须恰好有一个在跑** |
| `evolution` | 进化闭环还在不在转、转得对不对（CI 只能证明它能跑一次） |

加一项：`cp checks/_template.py checks/<名>.py`，不用改 `run.py`。
**这张表要跟着 `checks/` 一起改**——少一行就等于有一项巡检没人知道它在查什么。

## 两条铁律（写在 `checks/_template.py` 里）

1. **`why` 必填**——没有证据的判定是拍脑袋。巡检最大的失败不是漏报，
   是报一堆没人信的东西，然后所有人开始无视它。
2. **区分「查不了」和「没问题」**——目标不存在、权限不足时必须报 P2 说
   「这项没查成」，绝不能返回空当作通过。旧 patrol 就死在这一点上。

## 判据

1. **注入故障必须被检出**：制造「服务不存在」「心跳陈旧」「required 凭据缺失」
   三类故障，三项都要报出且级别正确。
   *2026-09-07 实测通过：P0/P1/P1，退出码 1。*
2. **不可逆动作绝不自动执行**：`systemctl stop`、删文件、改数据库一律
   报 P1 转人工，与 `mode` 无关。
   *2026-09-07 八个用例实测通过，含 `chown -R x:x /` 与重启 `sshd`——
   宾语不在 `config` 声明的对象里就不执行。*
3. **每轮必须留下 Task 与 Event**，且 `patrol_summary` 的 `failed_checks` 为空——
   非空说明有巡检项自己挂了，那块从此不再被覆盖。
4. **反复自愈必须升级**：同一动作第 3 次起报 P1。
   *一天 288 次「自愈成功」长得和「一切正常」一模一样——那是要杀的假绿。*
   *退避实测：1 次后等 10 分钟、3 次后等 1 小时，跨轮次有效。*

> **原判据第 4 条是「连续 7 天与旧 patrol 结论一致才可切 active」。**
> 那条已经无法满足——旧 patrol 随 `/opt/gooday` 退役，没有可比对象了。
> 2026-09-07 换成**按动作分级**而不是 `shadow`/`active` 二元：
> 幂等可回滚的（重启服务、修属主）放开，其余任何模式下都不自动执行。
> 换判据的理由见 `docs/decisions/003-patrol-cutover.md`。
