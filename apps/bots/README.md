# apps/bots · AI 员工

六个角色跑这家数字公司。规范在 `norms/C-*.md`（来自 `kits/ai-company-kit`）。

```
_core/          bot_common（公共库）/ dispatcher（规则调度）/ patrol（巡检兜底）
<角色>/         bot.py + prompt.md + README.md
```

## 三条架构铁律

1. **对外只有前台** —— 客户从咨询到售后只见一个角色，其余不可搜索/不可加好友。
2. **对上只有调度中心** —— 老板一单最多被打扰 2 次，其余进日报。
3. **调度靠事件表，不靠聊天** —— 流转凭证是数据库行。
   让调度 bot 转发消息会引入单点故障、每次流转多一轮大模型调用、以及
   "消息已读即凭证消失"。dispatcher 是**不调模型的纯规则进程**。

## 边界

- 心跳文件、`*-state.json`、pending 一律写 `/var/lib/gooday/state/`，**不在本目录**（G01）。
- 日志写 `/var/log/gooday/`（G01）。
- 每个角色的 `prompt.md` 必须包含注入防御条款——
  条款只写在文档里而没进 prompt，等于没有（真实教训，三个月没生效）。

## 判据

1. 一单从建单到交付，**打扰老板的实时消息 ≤2 条**（日报可统计）。
2. 任一 bot 被 `kill -9` 后，**巡检在阈值内自动拉起**；
   停写心跳后同样被发现——这两件事**不是同一回事**，都要演练过。
3. 大模型调用失败时，发送者**必须收到明确回执**；
   静默吞掉记为故障（历史上 8 次超时全部表现为"发消息没人理"）。
4. 改完常驻服务后，**进程启动时间晚于代码 mtime** 才算验过。
