# packages/botkit · AI 员工的共用底座

两个 bot（如意、灵犀）共用的那一层。从旧 `bot_common.py`（672 行）重新设计。

> 2026-09-11 起只剩两个使用方：擎天柱/威震天/招财/dispatcher 已随
> `docs/decisions/006` 删除。**本层的设计仍按「多个角色共用」来写**——
> 它的价值在于把「收件合并 / 幂等认领 / 失败必回执 / 出口白名单」这四件事
> 从角色里剥出来，角色数量减少不改变这一点。

**这里是本项目血泪教训最集中的地方。** 每条铁律后面都写了换来它的那次失败，
删之前先看那段注释。

## 三个模块

| | 管什么 | 核心铁律 |
|---|---|---|
| `model.py` | 调大模型 | 并发闸门 · Popen+killpg · 显式 `--model` · 区分基础设施错误 |
| `outbound.py` | 对外发送 | 出口白名单 · 重试+401 自愈 · 分段失败不 break |
| `inbox.py` | 收件处理 | 按发送者合并 · 幂等认领 · **失败必给回执** |

## 四条最贵的

**① 闸门坏了要放行，不是阻断。**
并发信号量是辅助设施。它自己出故障时返回「放行」——
宁可冒一次超载的风险，也不要让附属组件变成新的单点。

**② 未登记的角色默认拒绝发送。**
出口白名单是**结构性防线**：即使 bot 被 prompt 注入说服了，它也发不出去。
默认允许是安全灾难。

**③ 拦截要喊一声。**
静默拦截等于给攻击者一个安静的探测通道，也让正当的配置错误极难排查。

**④ `inbox.process()` 强制要求 `on_error` 回调。**
接口这样设计就是为了**让「静默吞掉」写不出来**——
历史上 8 次超时异常全部表现为「发消息没人理」，
标完已读就吞掉是最坏的处理方式：消息没了、人没收到、日志也看不出。

## 判据

1. **被 ≥2 个服务使用**——只剩 1 个调用方时应内联回去并删除本包。
2. **零第三方依赖**——它是最底层的包，被所有 bot 依赖，不能带包袱。
3. **自测覆盖「会真的坏」的路径**，不追覆盖率数字。
   *2026-09-07 实测 15 项全过：并发上限、闸门降级放行、基础设施错误识别、
   白名单默认拒绝、幂等认领、失败必回执。*

## 明确不做

- **不持有业务语义**——它不知道什么是工单、什么是客户。那是各 bot 的事。
- **不决定通知分级**——`notify` 的 P0~P3 路由属于业务层。
- **不管 prompt**——每个 bot 的 prompt 放各自的 `prompt.md`。
